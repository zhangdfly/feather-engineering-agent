# 用例：多阶段脚本需要足够完整的注释

## 模式

编写模式

## 输入

模块 README 已说明：云平台只接收一份首启文件，新机器不能访问仓库。控制端要把模板、安装脚本和每台机器的参数合成一份文件；产物含敏感入网密钥。

用户反馈“注释太少，不逐行阅读脚本就不知道它在做什么、为什么要渲染”。在不改变行为的前提下，补充下列脚本的注释。`render.py` 从环境读取 `JOIN_KEY`，把 `install.sh` 嵌入模板；脚本调用者已将 `JOIN_KEY` 导出。

```bash
#!/usr/bin/env bash
set -euo pipefail

# 生成首启配置。
: "${JOIN_KEY:?}"
: "${NODE_NAME:?}"
[[ "$NODE_NAME" =~ ^[a-z0-9]+$ ]] || exit 2

script_dir=$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)
output=$1
output_dir=$(dirname -- "$output")
mkdir -p -- "$output_dir"
temporary=$(mktemp "${output_dir}/.bootstrap.XXXXXX")
chmod 0600 "$temporary"
trap 'rm -f -- "$temporary"' EXIT

python3 "$script_dir/render.py" \
  "$script_dir/template.yaml" "$script_dir/install.sh" "$temporary" "$NODE_NAME"
mv -f -- "$temporary" "$output"
```

## 合格结果

- 文件头说明脚本在控制端将哪些输入合成为何种产物、由谁在首启时消费，而不只写“生成配置”；
- 关键阶段就地解释：参数检查只能验证密钥非空与主机名格式；为何从仓库取模板与脚本；为何在目标目录创建 `0600` 临时文件并注册退出清理；为何渲染成功后才替换目标文件；
- 略读文件头和阶段注释即可复述脚本的主要流程、顺序原因与失败后的产物边界，而不必逐行解释 Shell；
- 注释不声称密钥已经验证有效、失败时所有敏感副本必然清零或脚本会直接创建云主机；不改动现有行为。

## 失败特征

- 只在 README 或文件开头补一大段，脚本的关键阶段仍无就地说明；
- 用“阶段一：验证”“阶段二：渲染”等标题替换详细的顺序和失败原因；
- 为了避免冗余而删除必要注释，或对每行代码写一条语法翻译；
- 把 `JOIN_KEY` 非空说成已验证一次性、可用或已授权；把 `trap` 说成保证所有副本无条件被清理；
- 改写脚本行为来掩盖解释不足，而没有满足补充注释的请求。

## 边界条件

完全自解释的简单操作无须逐行注释；README 可以说明跨文件关系，但不能替代脚本内的执行阶段与失败边界。阶段说明可以多句，长度取决于读者理解流程所需的信息，而非固定注释数量。

## 反馈依据

用户明确要求注释更详尽，使读者不必逐行阅读代码也能理解主要流程与渲染的原因；不能把“注释应准确”误解为“应该减少注释”。
