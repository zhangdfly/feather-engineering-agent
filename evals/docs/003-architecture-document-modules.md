# 用例：复杂架构文档的模块组织与事实归属

## 模式

编写模式

## 输入

```text
把一份大型架构说明整理得更容易阅读。原文在同一个文件中依次包含：

- 系统组件关系；
- 初始化、发布、请求和恢复流程；
- 网络、权限、存储、成本等大量模块参数；
- 一张“关键决策”表，逐项重复后文已经写明的技术选择；
- 一张路径职责表，用来代替用户要求的仓库目录结构。

请保留所有有效约束，并按模块重新组织。可以使用一个或多个 Markdown 文件。
```

## 合格结果

- 先按职责、读者任务或生命周期识别模块，而不是套用固定文档层级；
- 内容较少时可以在同一文件中使用多个模块章节；只有独立受众、维护周期或阅读负担确实需要时才拆文件；
- overall 只表达跨模块关系，不逐个复述模块内容；流程放在拥有该流程的模块中；
- 参数、权限矩阵和验收标准各自只有一个权威归属，其他位置需要时直接链接；
- 删除没有新增取舍依据、状态或导航价值的重复“关键决策”表；
- 用从仓库根目录开始的树形结构表示目录，并区分已存在与计划中的路径；
- 保留原文中的有效事实、数值、安全边界和验证要求。

## 失败特征

- 不考虑内容规模和职责边界，强制拆成多个文件；
- 机械创建 overall、主要流程、决策摘要、模块细节等层级，并在每一层概括同一批模块；
- 仅调整标题或项目符号，没有形成职责清晰的模块；
- 总览、决策表和模块文档分别维护同一组参数或结论；
- 为了精简删除安全边界、数值或验收条件；
- 用“路径 / 职责”表冒充目录树；
- 把尚未创建的目录或文件写成当前仓库现状。

## 反馈依据

用户指出单体设计文档的大量列表难以阅读，随后进一步澄清：重点是按模块组织和消除重复，不应强制拆文件，也不应建立多个层级后在每层重复概括所有模块。用户同时确认重复的关键决策区应删除，并要求目录结构明确展示现状与规划。
