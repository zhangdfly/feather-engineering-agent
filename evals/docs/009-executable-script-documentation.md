# 用例：可执行脚本文档覆盖真实行为

## 模式

编写模式

## 输入

```text
这个目录有三个 shell：

- `versions.env` 由人维护组件版本；
- `prepare.sh` 读取版本，调用外部工具枚举关联镜像，再调用 `mirror.sh`；
- `mirror.sh` 逐个解析 Digest 并复制到远端仓库，全部成功后替换 `images.lock`；
- `verify.sh` 不带凭据读取锁中的远端 Digest。

复制到一半失败时，旧 lockfile 不变，但此前复制成功的远端镜像会保留。当前 README 只有“文件 / 职责 / 副作用”表和一张入口到 Registry 的时序图。

请重写 README，让维护者不读 shell 也能知道每个入口在做什么、为什么仍然需要 shell。
```

## 合格结果

- 明确 `versions.env` 是人工版本权威，脚本不会自行选择或修改版本；
- 分别说明 `prepare.sh` 的输入、外部枚举、兼容性检查和对共享实现的委托；
- 集中说明 `mirror.sh` 的参数与凭据、Digest 解析、逐项复制与复核、全部成功后替换 lockfile；
- 写清部分失败时旧 lockfile 是否保留、远端残留状态和安全重试方式；
- 说明 `verify.sh` 只读、无写凭据，并列出会阻止继续的关键条件；
- 解释 shell 用于外部查询、复制和生成不可变锁，而版本常量仍保存在声明文件；
- 可以保留职责表和时序图作为导航，但正文能够独立表达机制；
- 不逐行翻译 shell；相同共享流程只在 `mirror.sh` 一处完整说明，包装入口只写差异和委托。

## 失败特征

- 只扩充文件职责表、脚本头注释或时序图，没有写内部步骤和失败状态；
- 把“根据声明枚举镜像”误写成“shell 选择版本”；
- 只写最终 lockfile，不说明复制到一半失败后的远端残留；
- 声称失败无副作用或 lockfile 原子替换，却没有从真实实现确认；
- 在每个入口重复共享复制流程，或逐行解释命令语法；
- 因追求简短省略用户明确要求的行为与原因。

## 边界条件

只有一个固定参数并立即委托共享实现、没有独立校验或副作用的简单包装脚本，可以用一句话说明参数与委托并链接共享机制，不要求复制完整步骤。

## 反馈依据

用户指出 Agent 只写了脚本职责、版本结果和时序图，没有把 shell 内部实际动作、状态权威与部分失败边界写进 README，无法达到“不怎么看代码就知道在干什么”的目标。
