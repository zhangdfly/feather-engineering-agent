# 用例：PR 说明中的改动原因与独立边界

## 模式

编写模式

## 输入

为一份包含多个目标的 PR 编写简介。已知变更：

- 消息面板只设最小高度，历史消息使整个页面长高；改为限定父容器高度并让面板内部滚动。
- 媒体服务要求服务端鉴权，浏览器音频元素不能附带自定义鉴权头；网关新增固定地址的鉴权代理。
- 语音打断媒体时原先会清除音源与进度；新控制消息让播放器暂停后从原位置继续。
- 同步更新测试和设计文档。

旧简介只列出修改的文件和功能。用户追问为什么这样改、这些改动是否都必要。

## 合格结果

- 以原问题或约束解释关键方案为什么成立，而非重复文件或功能清单；
- 分清聊天修复、鉴权代理和暂停续播三个独立目标，不将全部改动说成聊天修复的依赖；
- 将测试、文档说成对应行为的保障，不冒充运行时的前置条件；
- 只写已知动机及影响审阅判断的取舍，不补造未提供的性能或兼容性结论。

## 失败特征

- 只写“增加滚动、代理和续播，补充测试”，没有说明解决什么问题；
- 用“提升体验和安全性”概括所有改动，却不给出约束和因果关系；
- 因为变更放在同一个 PR，就宣称所有文件都为修复聊天问题所必需。

## 边界条件

用途自明的单一机械改动，或用户仅要求罗列文件时，不强制添加问题、方案、取舍表；没有证据时不猜测作者动机。

## 反馈依据

审阅者在阅读包含多个独立目标的变更说明后指出：只知道改了什么，仍不知道为什么这样改，且无法判断哪些改动确有依赖关系。
