# 回归案例

`evals/` 记录规则需要防止的真实失败模式和不能误伤的合理结构。它不会在正常编写或 PR Review 时加载，也不会直接改变 Agent 行为。

评审结束后，如果用户反馈可以跨项目复用：

1. 更新拥有该职责的现有规则；
2. 在 `docs/` 或 `code/` 添加包含真实输入的最小回归案例；
3. 在同一个变更中提交规则与案例。

每个案例包含：

- `模式`：编写模式或 PR Review 模式；
- `输入`：最小提示、代码或 diff；
- `合格结果`：期望实现或期望 Review comment；
- `失败特征`：需要防止的遗漏、误报或错误结构。
- `边界条件`：相似但合理、不能被规则误伤的结构；不存在时可以省略。

PR Review 产生的案例还应包含 `反馈依据`，用一句匿名化描述说明用户指出了什么遗漏或误报。

案例应匿名化，只保留触发规则所需的结构。

## 评测方式

在同一宿主、模型和仓库状态下分别运行：

1. 不安装或不启用 Feather 的 baseline；
2. 启用 Feather 的 candidate；
3. 每个案例至少重复三次；
4. 按案例的合格结果、失败特征和边界条件判定；
5. 记录宿主、模型、日期、运行次数和失败样本。

不要只检查关键词。评测重点是最终结构是否降低阅读成本，同时保留正确性和合理边界。

`npm test` 验证版本、插件清单和案例章节完整性，但不调用模型，也不代表行为评测通过。
