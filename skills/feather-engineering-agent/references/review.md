# PR Review 与反馈学习

## 评审阶段

1. 读取 PR 描述、变更文件、diff、已有 Review comments 和讨论。
2. 根据变更内容加载代码规则、文档规则或两者。
3. 先检查正确性、安全、错误处理和资源边界，再检查 Feather 的可读性规则。
4. 不重复已有评论。每条评论必须指向具体变更，并说明问题、现实影响和需要修改的方向。
5. 不把尚未写入规则的个人偏好当作缺陷，不为没有实际影响的风格差异留言。
6. 用户要求发布时提交到 PR；否则生成可直接粘贴的评论。

评审进行中只处理当前 PR，不修改 Feather 规则。

## 评审结束后的学习

只有用户明确表示评审结束，或要求根据本次反馈更新 Feather 时，才执行：

1. 重新读取最终 diff、Agent 评论、用户评论、回复和处理结果。
2. 识别三类反馈：
   - 用户指出而 Agent 漏掉的问题；
   - 用户纠正或否定的 Agent 评论；
   - 用户明确要求成为通用规则，或多次出现且可以跨项目复用的判断标准。
3. 只沉淀可复现、可执行、可泛化的反馈。用户明确要求成为通用规则时，不要求它重复出现；项目特有约束、一次性取舍和纯个人措辞不进入通用规则。
4. 修改拥有该职责的现有规则；只有职责确实独立时才新增规则。
5. 在 `evals/code/` 或 `evals/docs/` 添加最小回归案例，记录模式、输入或 diff、期望行为、失败特征和匿名化的反馈依据。
6. 规则修改与回归案例必须放在同一个变更中。
7. 向用户说明吸收了哪些反馈、修改了哪些规则和案例，以及哪些反馈没有泛化。

回归案例应匿名化并保留导致问题的结构，不复制与规则无关的私有代码、人员信息或 PR 对话。
