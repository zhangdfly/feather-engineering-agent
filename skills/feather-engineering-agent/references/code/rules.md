## 代码结构规则

代码应让读者从权威编排入口直接看见业务顺序、状态所有者和失败边界。可读性优先于更少行数、更短函数和形式化分层。

### 流程可见性

具有明确 step 1-N 的线性 workflow，默认在一个权威编排入口（如 `run`）中按真实顺序展示。使用简短注释分隔业务步骤，注释应说明业务目的，而不是复述下一行语法。

允许多个公开 adapter 规范化不同形式的输入后委托给同一个编排实现，但不得复制、隐藏或重新排列流程。一个 workflow 只有一个权威步骤序列，不等于只能有一个公开方法。

允许抽取复杂步骤，但编排入口仍必须能通过准确的领域调用按顺序读出完整流程。

禁止 `run -> runWithLog -> bootstrap -> host -> execute -> process` 这类近义生命周期调用链。内部函数必须表达不同且真实的领域动作，不能只换一个“开始或执行”的动词。

### 抽取函数的条件

仅在至少满足一项时抽取：

1. 存在两个及以上真实调用点；
2. 具有独立领域概念、不变量、生命周期或错误语义；
3. 逻辑显著复杂，并且能够用稳定、准确的领域动作命名；
4. 需要隔离 I/O、锁、时钟、网络等副作用边界。

不要仅因为函数较长、追求层次整齐、套用设计模式或为未来预留扩展而抽取。

希望独立测试本身不足以证明应该抽取；被测试的代码还必须具有独立语义、不变量、算法或副作用边界。

把候选函数名当作调用点注释阅读。如果只能命名为 `run`、`start`、`process`、`handle` 或 `execute`，而不能说明实际动作，优先保持内联。

### 命名与所有权

名称必须反映真实领域动作、状态所有者、状态变化和作用域。把有副作用的调用读成一句话：

```text
receiver owns the state + verb names the transition + noun identifies the affected sub-state
```

方法应挂在真正拥有该状态或行为的对象上。裸 `start()` 只表示接收者自身开始生命周期；如果改变的是下属状态，方法名必须指出该状态。开始性能测量窗口应写成 `perfTracker.openMeasurementWindow()` 或 `measurementWindow.begin()`，不能用 `executor.start()` 隐藏真实行为。若 `Executor` 本身确实启动，则 `executor.start()` 是准确名称。

同一生命周期使用语义对称的动词对，例如 `open/close`、`begin/complete` 或 `start/stop`。类型、变量、方法、日志和测试使用同一领域术语。变量名应保留区分该状态所需的领域限定词；`openMeasurementWindow()` 的返回值应命名为 `measurementWindow`，不能缩写成丢失语义的 `window`。

避免使用 `Manager`、`Handler`、`Helper`、`Util` 等名称掩盖职责。

### 组合与类型

给已有类型增加日志、指标、重试等能力时，默认构造注入为成员，由真实业务方法直接使用。

wrapper、decorator、继承或代理仅在至少满足一项时使用：

1. 存在多个需要透明替换的被包装实现；
2. 同一横切策略需要独立组合到多种无关实现；
3. 包装层拥有不同且真实的资源生命周期；
4. 包装层增加独立不变量、错误语义或行为契约。

禁止：

- 没有明确边界价值的单实现接口；
- 只调用 `inner.method()` 的转发类或转发函数；
- 没有新状态、不变量或行为的嵌套类型；
- 只为命名对称建立的 `FooImpl`、`BaseFoo`、`AbstractFoo`；
- 仅为日志等单一能力建立的 `ExecutorWithLogger`。

### 正确性边界

不要以扁平化为由制造无法测试的巨型函数。复杂分支、独立资源生命周期、并发控制和副作用边界应保留为名称准确的领域单元。

根因修复优先于症状补丁：理解所有相关调用者，在共同责任点修复一次。

### 多阶段错误传播

命令流水线、发布流程和其他多阶段操作必须保留每个必要阶段的失败状态。不能只检查最后一个进程或最后一步的退出码，因为下游可能接受空输入或残缺产物并返回成功。

当下游成功不足以证明整体结果正确时：

1. 使用 `pipefail` 等运行时能力，或拆开执行并分别检查每个必要阶段；
2. 在产生副作用前验证交接数据的必要不变量；
3. 在完成后验证目标状态，而不是只确认目标对象存在。

值允许缺失、阶段明确为 best-effort，或下游自身会可靠拒绝残缺输入时，不要机械增加重复检查；代码必须让这种边界可见。

### 自检

- 只读权威编排入口，能否按顺序说出全部业务步骤？
- 多个公开入口是否委托给同一个步骤序列，而不是各自复制或重排流程？
- 每个抽取函数是否具有复用、独立语义、不变量、算法或副作用边界？
- 调用链中是否存在近义生命周期动词接力？
- 每个有副作用的方法名是否说明接收者真正拥有的状态变化？
- 每个 wrapper、接口、父类和嵌套类型是否增加真实能力？
- 任一必要阶段失败时，整体是否仍可能被最后一步报告为成功？
- 验证、错误处理、安全、并发和资源释放是否仍然完整？
