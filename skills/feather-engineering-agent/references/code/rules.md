## 代码结构规则

代码应让读者从公开入口直接看见业务顺序、状态所有者和失败边界。可读性优先于更少行数、更短函数和形式化分层。

### 流程可见性

具有明确 step 1-N 的线性 workflow，默认在一个 canonical 入口（如 `run`）中按真实顺序展示。使用简短注释分隔业务步骤，注释下面直接放对应代码。

允许抽取复杂步骤，但公开入口仍必须能按顺序读出完整流程。一个流程只有一个公开入口。

禁止 `run -> runWithLog -> bootstrap -> host -> execute -> process` 这类近义生命周期调用链。内部函数必须表达不同且真实的领域动作，不能只换一个“开始或执行”的动词。

### 抽取函数的条件

仅在至少满足一项时抽取：

1. 存在两个及以上真实调用点；
2. 具有独立领域概念、不变量、生命周期或错误语义；
3. 逻辑显著复杂，并且能够用稳定、准确的领域动作命名；
4. 需要独立测试，或需要隔离 I/O、锁、时钟、网络等副作用。

不要仅因为函数较长、追求层次整齐、套用设计模式或为未来预留扩展而抽取。

把候选函数名当作调用点注释阅读。如果只能命名为 `run`、`start`、`process`、`handle` 或 `execute`，而不能说明实际动作，优先保持内联。

### 命名与所有权

名称必须反映真实领域动作、状态所有者、状态变化和作用域。

方法应挂在真正拥有该状态或行为的对象上。开始性能窗口应写成 `perfTracker.startWindow()` 或 `window.begin()`，不能用 `executor.start()` 隐藏真实行为。

避免使用 `Manager`、`Handler`、`Helper`、`Util` 等名称掩盖职责。

### 组合与类型

给已有类型增加日志、指标、重试等能力时，默认构造注入为成员，由真实业务方法直接使用。

wrapper、decorator、继承或代理仅在至少满足一项时使用：

1. 存在多个需要透明替换的被包装实现；
2. 同一横切策略需要独立组合到多种无关实现；
3. 包装层拥有不同且真实的资源生命周期；
4. 包装层增加独立不变量、错误语义或行为契约。

禁止：

- 没有明确边界价值的单实现接口；
- 只调用 `inner.method()` 的转发类或转发函数；
- 没有新状态、不变量或行为的嵌套类型；
- 只为命名对称建立的 `FooImpl`、`BaseFoo`、`AbstractFoo`；
- 仅为日志等单一能力建立的 `ExecutorWithLogger`。

### 正确性边界

不要以扁平化为由制造无法测试的巨型函数。复杂分支、独立资源生命周期、并发控制和副作用边界应保留为名称准确的领域单元。

根因修复优先于症状补丁：理解所有相关调用者，在共同责任点修复一次。

### 自检

- 只读公开入口，能否按顺序说出全部业务步骤？
- 每个抽取函数是否具有复用、独立语义、不变量或测试边界？
- 调用链中是否存在近义生命周期动词接力？
- 方法名是否描述了接收者真正拥有的动作？
- 每个 wrapper、接口、父类和嵌套类型是否增加真实能力？
- 验证、错误处理、安全、并发和资源释放是否仍然完整？
