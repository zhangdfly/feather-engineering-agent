## 技术文档规则

技术文档应让读者按自然顺序获得正确结论或完成操作。简短仅在它提高可读性时有价值。

### 信息准入

一句话满足以下任一条件即可保留：

1. 直接回答用户明确提出的问题；
2. 完成操作或理解核心机制所必需；
3. 防止现实中的错误结果、操作失败、数据损失或安全问题。

删除后不影响正确理解和执行的信息应删除。

### 内容顺序

按需依次提供：

1. 结论、命令、参数值或解决方法；
2. 必要上下文和前置条件；
3. 会改变结论或操作的边界条件；
4. 完成任务、风险控制或复现确实需要的验证方式。

不要机械创建“前提”“注意事项”“验证”“总结”等章节。内容不存在时，章节也不应存在。

### 模块组织与事实归属

复杂文档先按职责、读者任务、状态所有者或独立生命周期识别模块，再决定模块放在同一文件的不同章节，还是拆成多个文件。内容较少且读者需要连续阅读时保留在一个文件；模块具有独立受众、维护周期，或单文件已经增加无关跳转时才拆分。文件数量和层级本身不是目标。

不要机械建立 overall、流程、决策摘要、模块细节等多层结构，并在每一层用一句话重复所有模块。跨模块图只表达组件关系，流程放在拥有该流程的模块中；其他位置需要引用时使用链接，不再复述参数和结论。

每个事实只指定一个权威归属。摘要、关键决策表或模块索引若只是重复正文已经完整表达的信息，应删除；仅当它增加取舍依据、状态、负责人或必要导航时保留。讨论过程中的备选项和排除项只有在会改变实现边界时才进入最终设计。

用户要求目录结构时，使用从仓库根目录开始的树形结构，并明确区分当前已存在与未来计划的路径；不要用职责表替代目录层级，也不要把规划文件表述为已经存在。

### 图表

当读者需要从多段文字中自行拼接组件关系或交互顺序时，应使用 UML 图直接表达：

- overall design 涉及多个组件、系统边界或依赖关系时，使用组件图；用 Mermaid `flowchart` 表达组件和依赖，用 `subgraph` 表达必要的系统边界；
- 核心逻辑涉及多个参与者的调用顺序、异步交互或关键分支时，使用 Mermaid `sequenceDiagram` 时序图。

目录树等只表达文件层级的内容不属于组件关系；文本树更清楚时不要转换成图。

图必须使用 `mermaid` 代码块并采用 GitHub 支持的 Mermaid 语法，不要用截图或只能通过外部工具查看的格式。图中的名称、方向和边界必须与正文及实现一致；正文只补充图中不适合表达的约束和结论，不要逐项复述图。

### 禁止模式

- 开场寒暄、问题复述和结尾客套；
- 未被询问的背景、历史、替代方案和排除项；
- 反驳读者没有提出的观点；
- 从多个维度重复同一结论；
- 空泛的重要性描述、意义升华和营销词；
- 多个限定词叠加形成的防御性措辞；
- 无根据的免责声明；
- 展示思考、讨论、草稿或改写过程；
- 用自然语言逐项复述代码、命令或配置已经明确表达的内容。

用户明确要求原理、报告、方案比较或详细分析时，应完整回答；不得以“精简”为由删掉问题本身。

### 生成与改写

生成新内容时，结论先行，只写通过信息准入的内容。

改写现有内容时：

- 每个保留句子都应给读者增加信息；
- 保留有依据且仍相关的事实、名称、数字、日期、命令、代码和链接；
- 不编造缺失信息；
- 默认只交付最终版本，不展示编辑过程。

### 自检

- 第一段是否已经给出答案或行动？
- 文档是否围绕职责清楚的模块组织，而不是为了形式建立多层摘要？
- 一个模块是否在 overall、流程、决策表和细节章节中被反复概括？
- 同一事实是否在多个章节或文件中形成了需要同步维护的副本？
- 是否回答了用户没有提出的问题？
- 是否存在删除后不影响理解和执行的句子？
- 注意事项是否真的会改变结论、操作或现实风险？
- 用户明确要求的内容与技术事实是否完整保留？
