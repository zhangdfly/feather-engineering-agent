# Feather Engineering Agent

## 可读性优先

先完整理解任务、现有实现和真实调用链，再决定代码和文档如何表达。

可读性是目标。减少代码、文字、层次或文件只是可能的手段；如果更短的实现隐藏流程、模糊所有权或增加跳转成本，应选择更容易顺序阅读的实现。

### 可读单元

每个句子、函数、类型和抽象层都必须增加至少一项：

- 新信息或直接答案；
- 完成任务所需的能力；
- 独立不变量、生命周期或错误语义；
- 更清晰的业务顺序、状态所有权、副作用、安全或测试边界。

否则删除、内联或合并。不要用改名、转发或分层重复表达同一件事，也不要为了减少行数把完整流程压缩成难读的表达式。

### 决策顺序

1. 用户是否真的要求它，或任务是否真的需要它？不需要就不添加。
2. 当前文档或代码是否已经表达或实现了它？优先复用。
3. 能否用现有语言、标准库、平台能力或已安装依赖直接完成？优先使用。
4. 只有前面都不成立时，才新增最小且完整的实现或说明。

该顺序用于降低阅读与维护成本，不得代替问题理解，也不得成为代码高尔夫。

### 不可裁剪

不得为了简短而删除：

- 用户明确要求的分析、行为或输出；
- 信任边界的输入验证；
- 防止数据损失的错误处理；
- 安全、权限、并发、取消与资源释放；
- 正确性所需的参数、事实与复现条件；
- 修复根因所需的调用链理解和测试边界。

交付核心结果和必要边界后停止。不要追加未请求的背景、辩护、总结或未来规划。

## 工作模式

### 编写模式

- 编写或修改技术文档时，读取 [references/docs/rules.md](references/docs/rules.md)。
- 编写或修改代码时，读取 [references/code/rules.md](references/code/rules.md)。
- 只有需要判断边界或解释规则时，才读取对应领域的 `examples.md`。
- 同时涉及代码与文档时，读取两组规则。

### PR Review 模式

用户提供 PR 链接或要求评审 PR 时：

1. 读取 [references/review.md](references/review.md)；
2. 根据变更内容读取代码规则、文档规则或两者；
3. 按用户要求草拟或发布具体、可执行的 Review comments；
4. 用户明确表示评审结束后，按 `references/review.md` 的源码仓库边界处理反馈：在 Feather 源码仓库中更新规则和 `evals/`，否则只生成候选 patch。

不要为了展示完整性加载无关领域的规则或示例。
